# Часть 2. Namespaces

Команды выполняются пользователем на удалённом Debian, от обычного пользователя, без `sudo`. Нужны Go, `unshare`, `nsenter`, `bash`, `ps`, `ip` и `curl`. При ошибке остановиться и сохранить её текст; не заменять запуск на `sudo unshare`, поскольку тогда изменится демонстрируемое отображение UID.

## 1. Подготовить бинарник

В каталоге `Lab1` на удалённом устройстве:

```bash
go build -o lab1-serv main.go
```

Бинарник нужен, чтобы главным процессом стал сам сервис, а не `go run`, запускающий сборку и дочерний процесс. Старый сервис из части 1 можно остановить через Ctrl+C в его терминале. Сохраните его PID 4348 в отчёте как результат предыдущего эксперимента.

## 2. Создать namespaces и исследовать их

В первом терминале, оставаясь в `Lab1`:

```bash
unshare --user --map-root-user --pid --fork \
  --mount --mount-proc --net --uts --ipc bash
```

`--fork` запускает дочерний процесс в новом PID namespace; `--mount-proc` монтирует `/proc` с его представлением процессов. `--map-root-user` отображает UID/GID обычного пользователя хоста в 0 внутри нового user namespace.

Теперь внутри полученной оболочки:

```bash
echo "Shell PID: $$"
id
hostname lab1
hostname
ps -eo pid,ppid,user,args
ip -brief address
ip route
```

Ожидается: оболочка имеет PID 1, UID внутри равен 0, hostname равен `lab1`; процессы хоста не видны. В новом network namespace есть только выключенный loopback, нет интерфейса хоста и внешних маршрутов. `ps` показывает также себя и другие временные процессы проверки.

Mount namespace отделяет таблицу монтирования; сам по себе он не создаёт отдельный корневой файловый набор. Файлы хоста на этом этапе ещё доступны. IPC namespace отделяет System V IPC и POSIX message queues.

Включить только loopback и заменить оболочку сервисом:

```bash
ip link set lo up
exec ./lab1-serv
```

`exec` заменяет оболочку, сохраняя PID 1. Сервис должен вывести `PID=1`. Loopback позволит обращаться к HTTP внутри namespace; связи с LAN этим не создаётся.

## 3. Проверить с хоста и войти внутрь

Во втором терминале того же удалённого устройства, под тем же обычным пользователем:

```bash
pgrep -u "$(id -u)" -x lab1-serv
```

Скопировать PID нового сервиса с хоста в переменную; ниже `12345` — пример, заменить фактическим числом. Если найдены несколько процессов, сначала выяснить, какой относится к этому запуску.

```bash
PID=12345
ps -o pid,ppid,uid,user,args -p "$PID"
cat "/proc/$PID/uid_map"
grep '^NSpid:' "/proc/$PID/status"
hostname
```

Ожидается: UID процесса на хосте — ваш обычный UID; `uid_map` показывает отображение 0 в этот UID; последнее число в `NSpid` — 1. Hostname хоста остаётся прежним.

Войти в namespaces процесса и проверить HTTP:

```bash
nsenter --target "$PID" --user --mount --net --pid --uts --ipc \
  bash -c 'id; hostname; ps -eo pid,ppid,user,args; curl -sS http://127.0.0.1:8080/health; echo'
```

Ожидается UID 0, hostname `lab1`, сервис с PID 1 и HTTP-ответ `ok`. Проверочные процессы `bash`, `ps`, `curl` тоже могут быть видны. Запрос из браузера к IP хоста теперь не достигает этого экземпляра: он слушает в отдельном network namespace, без veth и публикации порта.
