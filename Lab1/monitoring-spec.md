# Контракт мониторинга части 8

Статус: предложение для согласования, реализация не начата.

## Назначение

Снять временной ряд cgroup v2 контейнера lab1-gvisor на удалённом Debian и получить автономный HTML-дашборд для защиты. Python 3.13.5 доступен. Внешних Python-пакетов и новых сервисов не требуется. Измеряется cgroup sandbox на хосте, включая компоненты gVisor. Код HTTP-сервиса и его API не меняются.

## Артефакты и команды

Все пути относительно Lab1/ (на сервере ~/lab1).

- collect_metrics.py: чтение cgroup в течение указанного времени, CSV на стандартном формате Python csv.
- render_dashboard.py: преобразование сохранённого CSV в самостоятельный HTML с графиками SVG, без CDN и внешних запросов.
- results/monitoring.csv: фактические измерения пользователя.
- results/dashboard.html: графики этих измерений, открываемые как локальный файл в браузере.
- screenshots/: скриншот дашборда; Lab1.md: пояснения и обоснование трёх метрик для алертов.

~~~bash
python3 collect_metrics.py --cgroup "$CG" --output results/monitoring.csv --interval 2 --duration 180
python3 render_dashboard.py --input results/monitoring.csv --output results/dashboard.html
~~~

Сборщик работает вне cgroup приложения, только читает её файлы, не вызывает Docker и не создаёт нагрузку. Родительский каталог результата создаётся при необходимости; существующий файл не перезаписывается. Повторный опыт получает другое имя результата. Все действия запускает пользователь на сервере.

## CSV и расчёты

Одна строка на замер. Столбцы в следующем порядке:

~~~text
timestamp_utc,elapsed_seconds,memory_current_bytes,memory_max_bytes,cpu_quota_usec,cpu_period_usec,cpu_usage_usec,cpu_nr_periods,cpu_nr_throttled,cpu_throttled_usec,oom_kill,pids_current,pids_max,cpu_cores,cpu_limit_percent,throttled_periods_percent
~~~

- timestamp_utc: ISO 8601 UTC; elapsed_seconds: время от начала, по монотонным часам.
- Исходные значения берутся из memory.current, memory.max, cpu.max, cpu.stat, memory.events (oom_kill), pids.current и pids.max.
- Значение max в лимитах записывается как max; неизвестные/неприменимые производные значения — пустая ячейка.
- cpu_cores = delta(usage_usec) / (delta(time_seconds) * 1000000).
- cpu_limit_percent = cpu_cores / (quota / period) * 100 при конечной положительной квоте.
- throttled_periods_percent = 100 * delta(nr_throttled) / delta(nr_periods), если delta(nr_periods)>0. Это доля периодов, в которых было ограничение, не процент времени без CPU.
- Первый замер не имеет производных значений. Сброс счётчиков или изменение CPU-квоты исключают соответствующий интервал из расчёта.
- Ошибка чтения/исчезновение cgroup: понятное сообщение, ненулевой код завершения; ранее записанные строки сохраняются. Повторно созданная cgroup по тому же пути не должна незаметно продолжать старый ряд.
- Ctrl+C завершает сбор с сохранением уже записанных строк. Отсутствующие обязательные поля не заменяются нулями.

## Дашборд

Три графика с осью времени: память в МиБ и её лимит; CPU в ядрах и квота; доля периодов throttling в процентах. Подписи единиц, длительность записи и максимумы по доступным измерениям. Отдельно показываются OOM kill по приросту счётчика и пиковое pids.current. Исходные накопленные события не выдаются за события интервала. Данные первого замера и пропуски не отображаются как нулевые скорости. При пустом/некорректном CSV рендерер сообщает ошибку.

Это снимок записанного опыта, а не постоянно обновляемый сервер мониторинга. Алерты пока описываются в отчёте: пользователь выбирает три метрики, их пороги, длительность условия и последствия. Уведомления и Alertmanager в этот этап не входят.

## Критерии приёмки и следующий шаг

Пользователь снимает покой, умеренное выделение памяти и CPU-нагрузку в одном ряду; точные команды и размеры нагрузки выдаются на этапе опыта после подготовки сборщика. Расчёты сопоставляются с cpu.stat, HTML открывается в браузере и содержит графики реальных данных. Скриншот включён в отчёт. Численные результаты заранее не задаются. Локально сборщик, нагрузки и лабораторные проверки ассистент не запускает.
