# Контракт mydocker.sh

Согласован пользователем в диалоге перед реализацией.

- Среда: удалённый Debian 13 amd64, Linux 6.12, cgroup v2. Контроллеры memory, cpu и pids уже включены в корневом cgroup.subtree_control.
- Запуск: sudo ./mydocker.sh из Lab1. Аргументы не принимаются. SUDO_UID/SUDO_GID должны указывать на обычного пользователя.
- В каталоге скрипта обязательны исполняемый lab1-serv и непустой seccomp.bpf, подготовленные на удалённом устройстве. Компиляция и генерация профиля не входят в запуск.
- Профиль опыта: getppid возвращает EPERM, остальные syscall разрешены. Это демонстрационный фильтр, не производственная политика безопасности.
- Отдельная cgroup с уникальным именем lab1-<UID>-<PID>: memory.max=134217728, memory.swap.max=0, cpu.max="50000 100000", pids.max=64. Процессы запускаются в группе с самого начала; управляющий процесс остаётся снаружи.
- Возврат к UID/GID вызывающего пользователя предшествует созданию user namespace. Затем создаются user, pid, mount, net, uts, ipc namespaces с отображением текущего пользователя в root и новым /proc.
- Внутри сначала устанавливается hostname lab1 и поднимается loopback, затем удаляются capabilities, устанавливается no_new_privs и загружается seccomp.bpf. Сервис заменяет оболочку через exec и получает PID 1. HTTP-порт фиксирован: 8080.
- Скрипт проверяет членство в cgroup, PID 1, CapEff/CapPrm/CapBnd/CapInh/CapAmb=0, NoNewPrivs=1, Seccomp=2 и ответ /health=ok. При ошибке запуска печатает диагностику, завершает свою группу и возвращает ненулевой код.
- Выводит путь cgroup, PID сервиса на хосте, исходный UID и команду проверки HTTP через sudo nsenter --net. Публикация порта в сеть хоста отсутствует.
- Нормальное завершение сервиса сохраняет его код выхода. INT/TERM/HUP завершают запуск с кодами 130/143/129. Очистка использует cgroup.kill и rmdir только для созданной этим запуском группы. Ошибка очистки явно сообщается и даёт ненулевой код.
- shortcut: SIGKILL управляющего скрипта и отключение питания не позволяют выполнить trap; при необходимости ручной очистки используется напечатанный путь cgroup.
- Корневая файловая система остаётся хостовой; rootfs, образ, veth, volumes, журналирование и перезапуск не добавляются. Это этап сборки уже изученных механизмов, сравнение с Docker выполняется после проверки запуска.

## Проверка пользователем

1. Запустить скрипт на Debian, получить успешную встроенную проверку и /health через напечатанную команду nsenter.
2. С хоста проверить UID, NSpid, CapEff, NoNewPrivs, Seccomp и четыре файла лимитов; сохранить скриншот.
3. Остановить через Ctrl+C и убедиться, что напечатанная cgroup удалена. Повторить с SIGTERM управляющему PID, напечатанному скриптом.
4. При отдельном повторном запуске вызвать /eat?mb=256 через nsenter: ожидается OOM и удаление cgroup после завершения. Если нужны счётчики OOM после опыта, использовать сохранённый отдельный эксперимент части 3: данный скрипт удаляет свою группу.

Статус: контракт согласован; пользователь подтвердил успешную проверку синтаксиса, встроенную самопроверку запуска, HTTP-ответ ok и удаление cgroup после Ctrl+C (2026-10-16). Отдельные проверки SIGTERM и OOM объединённого скрипта ещё не выполнены.

## Запуск и проверка на удалённом Debian

Все команды ниже выполняет пользователь в каталоге Lab1. Бинарник и BPF-профиль, созданные на сервере, не нужно запускать на локальном Windows.

Если бинарник или профиль отсутствуют, подготовить их на сервере:

~~~bash
go build -o lab1-serv main.go
enosys --syscall getppid:EPERM --dump=seccomp.bpf
~~~

Сохранить mydocker.sh с окончаниями строк LF, проверить синтаксис и запустить:

~~~bash
chmod +x mydocker.sh
bash -n mydocker.sh
sudo ./mydocker.sh
~~~

Скрипт напечатает MANAGER_PID, CGROUP и после успешной проверки — HOST_PID и готовую HTTP-команду. Сохранить весь вывод. Самопроверка выполняется при запуске на сервере; успешный запуск описан в отчёте.

Во втором терминале подставить фактические значения из вывода (12345 и путь ниже — примеры):

~~~bash
PID=12345
CG=/sys/fs/cgroup/lab1-1000-12300
sudo nsenter --target "$PID" --net curl --noproxy '*' -fsS http://127.0.0.1:8080/health
echo
ps -o pid,ppid,uid,user,args -p "$PID"
grep -E '^(NSpid|Uid|Cap(Inh|Prm|Eff|Bnd|Amb)|NoNewPrivs|Seccomp):' "/proc/$PID/status"
cat "$CG/memory.max" "$CG/memory.swap.max" "$CG/cpu.max" "$CG/pids.max"
sudo nsenter --target "$PID" --user --mount --pid --uts hostname
~~~

Ожидаемые результаты: ok; UID 1000 на хосте; последнее число NSpid — 1; нулевые Cap-поля; NoNewPrivs=1; Seccomp=2; лимиты 134217728, 0, 50000 100000, 64; hostname lab1. Проверка через nsenter создаёт отдельный проверочный процесс: его capabilities не следует принимать за capabilities сервиса. Их проверяем в /proc/$PID/status с хоста.

После Ctrl+C в первом терминале проверить из второго:

~~~bash
test ! -d "$CG" && echo "cgroup удалена"
~~~

Отдельно проверить SIGTERM при повторном запуске: передать его новому MANAGER_PID через sudo kill -TERM, затем проверить удаление новой cgroup. При ошибке очистки не удалять другие группы: прислать диагностику и напечатанный путь.

Сохранить в screenshots/ вывод успешной самопроверки, /health, PID/UID/capabilities/seccomp, лимиты и удаление cgroup. Добавить ссылки в Lab1.md.
