## Текущий шаг: исходный замер

Удалённый Debian, ~/lab1. Контейнер lab1-gvisor должен оставаться running. Если он остановлен, сначала прислать inspect/logs, не читать cgroup по PID 0.

~~~bash
cd ~/lab1
command -v python3
python3 --version
sudo docker inspect --format 'Status={{.State.Status}} PID={{.State.Pid}}' lab1-gvisor
~~~

Если Status=running и PID положительный:

~~~bash
PID=$(sudo docker inspect --format '{{.State.Pid}}' lab1-gvisor)
CGPATH=$(sudo awk -F: '$1=="0" {print $3}' "/proc/$PID/cgroup")
CG="/sys/fs/cgroup$CGPATH"
printf 'Cgroup=%s\n' "$CG"
for name in memory.current memory.max memory.events cpu.max cpu.stat pids.current pids.max; do
  printf '\n%s\n' "$name"
  sudo cat "$CG/$name"
done
~~~

Сохранить и прислать вывод. Пока нагрузку не включать. memory.current — текущее потребление cgroup; usage_usec — накопленное CPU-время, не готовый процент. Для графика CPU нужны разности двух замеров и прошедшее время. Аналогично доля периодов throttling вычисляется по разностям nr_throttled/nr_periods; это не процент времени без CPU. Исходные данные и формулы должны оставаться проверяемыми.

Источник: [cgroup v2, документация ядра Linux](https://docs.kernel.org/admin-guide/cgroup-v2.html).

Статус: исходный замер выполнен пользователем, Python 3.13.5 доступен. memory.current=25235456, memory.max=134217728, OOM-событий нет, usage_usec=5152759, nr_periods=4326, nr_throttled=1, throttled_usec=156957, pids.current=28, pids.max=64. Сбор данных во времени и дашборд ещё не выполнены. До следующего этапа проверить понимание накопительных счётчиков и интервалов.

Понимание исходного замера проверено: за 10 секунд прирост CPU-времени 5 секунд означает 0,5 ядра и 100% квоты; неизменный nr_throttled означает отсутствие новых периодов throttling. Подготовлен monitoring-spec.md; перед реализацией требуется согласование контракта.
