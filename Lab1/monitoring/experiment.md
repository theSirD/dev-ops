## Требуемые панели

Дашборд Lab1 — lab1-gvisor: память, CPU и throttling. up можно сохранить отдельным индикатором доступности cAdvisor; он не заменяет throttling и не является проверкой HTTP /health приложения. Time series панели используют Range-запросы; период Last 15 minutes, обновление 5s/10s. Источник Prometheus. Сохранить dashboard в Grafana.

Память в МиБ (unit mebibytes):

~~~promql
container_memory_usage_bytes{job="lab1-host-cadvisor",name="lab1-gvisor"} / 1024 / 1024
~~~

Вторая линия той же панели — лимит:

~~~promql
container_spec_memory_limit_bytes{job="lab1-host-cadvisor",name="lab1-gvisor"} / 1024 / 1024
~~~

CPU в ядрах (unit short, название CPU cores):

~~~promql
rate(container_cpu_usage_seconds_total{job="lab1-host-cadvisor",name="lab1-gvisor"}[1m])
~~~

Добавить threshold 0.5, соответствующий проверенной квоте cpu.max=50000 100000. Сырые накопленные секунды CPU не являются графиком текущей нагрузки.

Throttling, unit Percent (0-100), min 0, max 100:

~~~promql
100 *
rate(container_cpu_cfs_throttled_periods_total{job="lab1-host-cadvisor",name="lab1-gvisor"}[1m])
/
rate(container_cpu_cfs_periods_total{job="lab1-host-cadvisor",name="lab1-gvisor"}[1m])
~~~

Это доля CFS-периодов, в которых было ограничение, а не доля времени без CPU. Если за окно нет новых периодов, деление 0/0 даёт NaN/разрыв; это не повод менять формулу или подставлять фиктивные данные. В режиме нагрузки должны появиться новые периоды. rate учитывает сбросы счётчика при перезапуске.

## Опыт на удалённом сервере

Команды выполнять в отдельной SSH-сессии, не прерывая Grafana port-forward и SSH-туннель. До опыта убедиться, что lab1-gvisor running и health отвечает. Если уже включён burn или память выросла от прошлых опытов, сначала сообщить результат — не повторять выделение памяти бесконтрольно.

~~~bash
sudo docker inspect --format 'Status={{.State.Status}}' lab1-gvisor
curl --noproxy '*' -fsS --max-time 10 http://127.0.0.1:8083/health
printf '\n'
~~~

1. Записать примерно минуту без новой нагрузки, оставить Grafana автообновляться.
2. Отметить время и один раз выделить 32 МиБ:

~~~bash
date -Is
curl --noproxy '*' -fsS --max-time 10 'http://127.0.0.1:8083/eat?mb=32'
printf '\n'
~~~

Подождать около минуты, наблюдать изменение памяти. Исходный замер был около 24 МиБ, лимит 128 МиБ, 32 МиБ выбраны как умеренная нагрузка, а не повторение OOM. Не запускать запрос многократно: память накапливается.

3. Отметить время и один раз включить CPU-нагрузку:

~~~bash
date -Is
curl --noproxy '*' -fsS --max-time 10 http://127.0.0.1:8083/burn
printf '\n'
~~~

Наблюдать около двух минут. Ожидается рост CPU примерно к 0,5 ядра и повышение доли периодов throttling; точные значения не предполагаются заранее, у gVisor есть накладные расходы. Проверить health под нагрузкой:

~~~bash
curl --noproxy '*' -fsS --max-time 10 http://127.0.0.1:8083/health
printf '\n'
~~~

Сохранить скриншот всех панелей с временной шкалой в Lab1/screenshots/monitoring-load.png и экспорт JSON дашборда в Lab1/monitoring/dashboard.json. На удалённой машине каталог проекта ~/lab1; экспорт браузер скачивает на компьютер пользователя, файл сохраняется/переносится в локальный Lab1/. Прислать фактические значения и скриншот для отчёта.

4. После фиксации результата выключить нагрузку перезапуском только подопытного контейнера (burn работает до завершения процесса):

~~~bash
date -Is
sudo docker restart lab1-gvisor
curl --noproxy '*' --retry 10 --retry-connrefused --retry-delay 1 \
  -fsS --max-time 5 http://127.0.0.1:8083/health
printf '\n'
~~~

Это завершит burn и освободит память приложения. Контейнер остаётся с тем же Docker ID/настройками, PID может измениться, счётчики cgroup могут сброситься. Графики сглажены окном rate, поэтому CPU не обязан мгновенно отобразиться нулём. Не перезапускать Prometheus/cAdvisor/кластер. При ошибках сохранить вывод.
