# Часть 6: образы и хранение данных — план выполнения

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking. Альтернативное выполнение через superpowers:subagent-driven-development — только по отдельному выбору пользователя. Сборки и команды лабораторной выполняет исключительно пользователь на удалённом Debian.

**Goal:** Собрать два образа одного сервиса, сравнить размер, слои и кэш, доказать различие writable layer и volume.

**Architecture:** Обычный образ сохраняет Go toolchain и исходники. Multi-stage использует тот же сборщик, но переносит только статический бинарник в scratch. Для файловых экспериментов используется обычный образ с shell; API сервиса не расширяется.

**Tech Stack:** Debian 13 amd64, Go 1.24.4, Docker Engine 26.1.5, стандартный docker build, scratch, named volume.

**Spec:** [images-spec.md](images-spec.md), согласован пользователем 2026-10-16.

## Global Constraints

- Все изменения находятся в Lab1/, ветка lab1. Чужие изменения и скриншоты сохраняются.
- Ассистент подготавливает файлы и объяснения; пользователь выполняет pull, build, run, inspect и проверки на сервере.
- go.mod: module main, go 1.24.4. Исходный main.go и HTTP-контракт не меняются.
- Оба сборщика: golang:1.24.4; одинаковая команда CGO_ENABLED=0 go build -trimpath -o /lab1-serv .
- Оба конечных образа: USER 1000:1000, ENTRYPOINT ["/lab1-serv"], EXPOSE 8080.
- Теги: lab1-api:single и lab1-api:multi. Размеры, времена и число слоёв не заполняются до измерения.
- Не очищать кэш, не использовать prune и не удалять существующие тома ради эксперимента.

## Review Focus

1. Тег сборщика или BuildKit недоступен: получить фактическую ошибку, не менять Go и инструменты молча.
2. Лишние файлы попали в контекст: .dockerignore допускает только main.go, go.mod и Dockerfile-файлы.
3. Scratch не запускается из-за динамических зависимостей: CGO_ENABLED=0 и реальный HTTP-тест обоих образов.
4. Число инструкций принято за число слоёв: файловые слои считать через RootFS.Layers, историю смотреть отдельно.
5. Потерю данных спутали с restart или правами доступа: удалить и создать контейнер заново; для обеих тестовых записей использовать docker exec --user 0.

### Задача 1. Подготовить и проверить два образа

**Files:** создать go.mod, Dockerfile.single, Dockerfile, .dockerignore, part6-images.md.

**Interfaces:** вход — согласованный модуль и существующий main.go; выход — образы lab1-api:single и lab1-api:multi с одинаковым HTTP API.

- [x] Ассистент создаёт точный go.mod; оба Dockerfile используют одинаковые WORKDIR, COPY и команду компиляции в стадии сборки. В Dockerfile.single нет второй стадии; в Dockerfile финальная стадия scratch получает только /lab1-serv.
- [x] Ассистент ограничивает контекст через .dockerignore и пишет команды проверки в part6-images.md. Dockerfile не использует COPY всего каталога, дополнительных зависимостей и скриптов запуска.
- [x] Пользователь проверяет доступность golang:1.24.4 и наличие buildx. Сохраняет digest сборщика. Для BuildKit используются логи с --progress=plain; если доступен только legacy builder, это отдельно фиксируется, без принудительной установки другого builder.
- [x] Пользователь собирает single и multi стандартным docker build с нужным -f и -t. При ошибке останавливается и присылает вывод.
- [x] Пользователь запускает оба образа под разными именами: lab1-images-single и lab1-images-multi; порты хоста 8081 и 8082 соответственно направлены на 8080. Используются лимиты памяти 128 MiB, swap 0, CPU 0,5 и 64 задачи, cap-drop ALL и no-new-privileges.
- [x] Проверка каждого запуска: HTTP 200 и точное тело ok на /health. Через image inspect подтвердить USER 1000:1000 и ENTRYPOINT ["/lab1-serv"]. Сохранить вывод и снимок screenshots/part6-health.png. Логи ошибок scratch не подменять предположением о нехватке shell.

### Задача 2. Сравнить размер, слои и кэш

**Files:** команды в part6-images.md; результаты и снимки в Lab1.md и screenshots/.

**Interfaces:** вход — оба рабочих образа задачи 1; выход — измеренные значения и доказательство повторного использования кэша.

- [x] Пользователь получает .Size в байтах, .Id и len .RootFS.Layers для обоих тегов через docker image inspect. Отдельно сохраняет docker history --no-trunc для каждого.
- [x] Пользователь повторяет обе сборки с теми же тегами и неизменными входами. Не добавлять --no-cache, --pull или очистку builder.
- [x] В логах найти CACHED у BuildKit или Using cache у legacy builder; записать, какие COPY/RUN переиспользовались. Учесть, что первая multi-stage сборка уже может использовать кэш, созданный single-сборкой.
- [x] Ассистент заполняет в отчёте таблицу: тег, ID, размер в байтах, число файловых слоёв, кэш. Снимки: screenshots/part6-images.png и screenshots/part6-cache.png. Не считать USER/EXPOSE/ENTRYPOINT отдельными файловыми слоями.
- [x] После выполнения ассистент задаёт 2–3 вопроса: что исключено из конечного scratch, зачем статический бинарник, что определяет попадание COPY/RUN в кэш. К следующей задаче переходить после правильных ответов и фактических результатов.

### Задача 3. Доказать время жизни файлов

**Files:** дополнить part6-images.md текущим экспериментом; результаты в Lab1.md и screenshots/part6-storage.png.

**Interfaces:** вход — обычный образ lab1-api:single с shell; выход — два контрольных наблюдения без изменения HTTP API.

- [x] После прохождения задачи 2 ассистент выдаёт команды только текущего файлового эксперимента.
- [x] Пользователь создаёт отдельный тестовый контейнер lab1-files из single-образа. Через docker exec --user 0 записывает известную строку в /tmp/lab1-proof.txt и читает её обратно.
- [x] Пользователь удаляет этот контейнер и создаёт новый из того же неизменённого образа, без volume. Проверяет именно отсутствие /tmp/lab1-proof.txt, а не только ошибку чтения. Обычный stop/start или restart не заменяет пересоздание.
- [x] Пользователь создаёт новый named volume lab1-images-data. Если такой уже существует, работа останавливается для выбора свободного имени; существующие данные не очищаются.
- [x] Пользователь подключает volume к /lab-data, через docker exec --user 0 записывает контрольную строку в /lab-data/lab1-proof.txt. После удаления и пересоздания контейнера с тем же volume проверяет точное содержимое файла.
- [x] Пользователь удаляет только тестовые контейнеры. Том сохраняется для защиты; его удаление не является частью эксперимента. Приложение всё время работает как UID 1000:1000, root используется лишь для диагностической записи, чтобы не спутать хранение с правами.
- [x] Ассистент проверяет понимание: почему restart сохраняет writable layer, почему файл исчез после пересоздания, почему volume сохранился. Ошибки разбираются до перехода к части 7.
